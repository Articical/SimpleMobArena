# Paper 26.3 staging acceptance checklist

Run these on a staging copy using Java 25, the exact deployed Paper build, Vault, EssentialsX and your usual protection/teleport/inventory plugins. Keep production currency and player data separate. Record plugin versions, configuration, session IDs, console logs and before/after balances. Take a full backup before crash testing.

For inventory checks, use distinct named/enchanted items, damaged armor, offhand gear, XP, effects and nondefault food/health. Record every slot before joining and after leaving/recovery. Confirm no duplicate inventory, dropped items, unowned kit items or unexpected XP exist. Confirm console errors are absent or expected and clearly explained.

| Scenario | Procedure | Acceptance criteria |

| Achievement service availability | Start with no MineplayAchievements plugin, then the full plugin with delayed database startup. Check `/ma admin achievements status` and resync a stored UUID | Core arenas and payouts work without the API; live kill checkpoints continue to persist. Sources register before definitions and progress; stored players, including unfinished checkpoint records, replay after readiness. No main-thread SQL, blocking future wait, or duplicate AP from repeated absolute totals |

SQL/API work does not stall the server thread; slow services can delay presentation |
| Typed kill attribution and finalization | Kill zombies, husks, regular/rapid-fire skeletons, direct wave vexes and summoned vexes across concurrent arenas. Inspect live checkpoints, finish and restart; inspect `participant_mob_kills` and central sources | Each valid player kill records once by actual mob type in its own session. A not-yet-committed batch can be lost; no synchronous durability claim is made for every kill |

Repeat with the final kill ending the match while a checkpoint is pending | Combat stays responsive and uncommitted counts are not reported as durable achievements. A completed match reconciles with its pending checkpoint once; checkpoint failure does not manufacture a payment or block healthy equipment restoration |

For restart tests, a normal `stop` verifies graceful shutdown only. An abrupt process termination test is a separate requirement. Vault crash-boundary tests require a controlled provider/test harness that can pause a deposit at known points; merely restarting after a normal match does not validate uncertainty handling.

For class configuration recovery, start with one potion missing `potion.base-type`/effects, then with malformed `classes.yml`. Valid kits should remain available when the document can be parsed; invalid classes must never equip partially. Personal gear must follow the configured mode, and CLASS mode must not fall back to personal gear. Ordinary logins and outstanding inventory restoration should continue when snapshot storage is healthy. Repair the YAML and reload while idle; the class should become available and stale unlock callbacks must not equip an old kit. Repeat with genuinely unavailable snapshot storage: recovery protection must still refuse unsafe startup.

Before deployment, obtain passing evidence for every financial/inventory row and inspect the unchanged ordinary survival area below the arena. Remaining failures or untested critical rows block a production-ready claim.
